# Security policy

## Supported versions

Only the live site at [nextsode.cloudils.com](https://nextsode.cloudils.com) is supported. It deploys from `main` on every merge, so fixes ship there and nowhere else.

## Reporting a vulnerability

Please report privately through [GitHub's private vulnerability reporting](https://github.com/Isma-L154/nextsode/security/advisories/new). If you cannot use GitHub, email info@cloudils.com. Do not open a public issue.

Include the affected URL or file, the steps to reproduce, and what an attacker gains. You can expect a first reply within 7 days. Please give a fix a reasonable time to ship before you disclose.

## Baseline security controls

1. **Secrets in environment variables: implemented.** No secret is committed (gitleaks finds nothing in the tree or the history), `.env.example` lists secret keys with no values and public local-container credentials, and production secrets live in Cloudflare. `src/env.ts` declares `TMDB_ACCESS_TOKEN` as required: a Worker has no startup phase, so SvelteKit validates it when the first request initializes the server, and every request fails with "Invalid environment variables" until it is set. Database requests require `env.HYPERDRIVE.connectionString`; the request creates one lazy node-postgres pool with `max: 1` and closes it after the response. Owner credentials (`DATABASE_URL`) are used by drizzle-kit and local Docker setup; the Worker connects as `nextsode_app`. The example connection strings are public local-container credentials, never production secrets. The Google variables stay optional because they switch sign-in on and off, not because the app can run without a value it needs.
2. **CORS: implemented.** No route sends CORS headers, so every endpoint is same-origin only. Nothing relies on CORS for authorization: form actions go through SvelteKit's origin check, and data is scoped to the session's user.
3. **Backend validation: implemented.** Every input is read through a valibot schema in `src/lib/server/validation.ts`: form bodies, query strings, path parameters, the OAuth callback and the share and calendar tokens. Schemas are strict allowlists. An unknown or repeated field, an uploaded file, an out-of-range number, a number written in any but the plain form, or an overlong string is refused with a 400 (a 404 for tokens), never truncated, clamped or replaced with a default. Form bodies are capped at 32 KB, counted as the bytes arrive rather than taken from `content-length`. Inputs are flat key-value fields, so there is no nesting depth to bound. The OAuth callback alone ignores parameters it does not declare, because Google appends its own. `validation.spec.ts`, `actions.spec.ts` and `page.server.spec.ts` cover the refusals.
4. **Sanitize before storage: implemented.** Every runtime query goes through Drizzle with bound parameters, including the SQL templates used to call the database functions. The one-time copy script uses Drizzle schema inserts with bound parameters. Svelte escapes every rendered value, and JSON-LD escapes `<` before it is embedded. No user input reaches a file path, a shell or a deserializer.
5. **Rate limiting: implemented.** The Worker is the only layer that exists here (no separate API gateway or database proxy), and it carries three Workers rate-limit bindings (`wrangler.jsonc`, applied through `src/lib/server/rate-limit.ts`). `API_RATE_LIMIT` allows 60 requests per minute per `CF-Connecting-IP` on the public TMDB proxies, the title page and the shared list page, and per feed token on the calendar feed. `AUTH_RATE_LIMIT` is stricter on sign-in: 10 requests per minute per IP across the start and the callback of the Google flow. `ACCOUNT_RATE_LIMIT` allows 60 form actions per minute per signed-in account, whatever IP they come from. Each limit was triggered against the built Worker (`wrangler dev`) or the dev server and answered 429 past its ceiling; `actions.spec.ts` checks that the account limit is keyed by the user id and stops the write. The bindings are approximate, as Cloudflare documents: they stop one loop, not a distributed caller.
6. **Row Level Security: implemented.** All application tables live in the dedicated `nextsode` schema in Supabase Postgres. The read-only `nextsode_backup` role has `BYPASSRLS` for backups only, with no write or function access. The non-owner `nextsode_app` role has neither superuser nor BYPASSRLS privileges and receives only the required table privileges. Separate policies per operation default to deny and use a transaction-local identity, set only by `withUser(SessionUser, work)` from the validated session. Owner predicates remain in application queries as the first layer. Shared TMDB metadata is readable and writable only with an identity; the server fetches its values from TMDB, never the add form. Session lookup, Google sign-in, shared lists and calendar feeds use four narrow `SECURITY DEFINER` functions owned by `postgres`, with an empty `search_path`, qualified names and explicit return columns. `PUBLIC`, `anon` and `authenticated` have no schema, table or function access. `src/lib/server/db/security.spec.ts` covers cross-account isolation, no-user denial, transaction identity reset, role ownership and privileges, function output and token matching; `actions.spec.ts` covers forged inputs and the atomic per-user cap.
7. **Content Security Policy: implemented.** SvelteKit generates the policy per response (`csp` in `vite.config.ts`). It sets `default-src 'self'`, a hash-based `script-src` and `style-src 'self'` with no `unsafe-inline` or `unsafe-eval`, `object-src 'none'`, `base-uri 'none'` and `frame-ancestors 'none'`. Server-rendered markup carries no inline style attribute; the one style attribute the client creates, on SvelteKit's route announcer, is allowed by its exact hash under `style-src-attr`, and `src/csp.spec.ts` fails if a SvelteKit update changes it. `src/hooks.server.ts` adds HSTS, `X-Content-Type-Options: nosniff`, `Referrer-Policy`, `X-Frame-Options` and `Permissions-Policy` to every response.

## Continuous scanning

Gitleaks checks committed secrets, semgrep checks vulnerable code patterns, osv-scanner checks vulnerable dependencies while honouring `osv-scanner.toml`, and zizmor checks unsafe workflow configuration. They run on every pull request and push to `main` through `.github/workflows/security.yml`. The `main` ruleset requires all four checks to pass before a pull request can merge.
